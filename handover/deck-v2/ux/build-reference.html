Agentic Kinetic · build reference

Everything needed to build the patient app and the Clinic Board against the backend that already exists. It covers what the agent does at each step, which route it calls, what comes back, which widget shows it, and the rules the build must keep. The two HTML boards are the visual reference; this page is the behaviour.

Visual references: deck-v2/ux/screens/patient-widget-final.html · deck-v2/ux/screens/clinic-board-final.htmlReal backend output: deck-v2/ux/data/backend-capture.json

Section 2

Rules that never change

These are the regulatory design, not style. Each is already enforced in Python; the frontend must not undo it.

Two channels, two payloads

  • The patient app never mounts the agent. It reads GET /api/patient/view only: no stream, no shared state, no agent thread. Agent shared state is replicated to every client on a thread, so a mounted patient session would hold the prediction in the browser even if nothing displays it.
  • Never send the clinician payload to the patient app and hide fields. A hidden field is still on the wire.
  • The Clinic Board mounts the agent and renders the clinician view.

The patient app interprets nothing

  • Never on the patient app: a drug level, a prediction, an interval, in or out of range, which way a level is moving, dose advice, an interaction verdict, urgency, a countdown, anything about the kidney.
  • Software-written patient text contains no digits. Exempt: the clinician's own plan text, her own doses and times, booked times and phone numbers.
  • A health question is never answered. It goes to the care team.
  • Instructions reach her only in her clinician's own words.

The gate and the pause

  • No language model decides whether to escalate. The gate is deterministic Python reading Prediction.crosses_boundary.
  • The pause is a LangGraph interrupt() the frontend renders and answers. The frontend cannot create, suppress or skip it.
  • The only answers are "accepted" and "declined". Anything else is rejected, never defaulted.

The Clinic Board shows its basis

  • Never a dose amount written by the software, and no "change dose" button.
  • Never a line joining measured troughs. Troughs are dots; the prediction is a range bar.
  • Never a number without its range, and never a claim without its source behind "Sources".
  • review_required is never shown as steady. magnitude_ng_per_ml: null is never shown as 0. variability: null always shows its reason.

Section 3

What the backend serves the Clinic Board

Every number on the Clinic Board arrives in the clinician response itself. The board never reads the patient route, never parses evidence prose, and never computes a clinical figure of its own. Two blocks make that true:

BlockSent withWhat it carries
prediction, variability, variability_unavailable_reasonawaiting_decision (inside clinician_view once complete)The prediction that raised the offer, so the decision card can show "57 in 100", the predicted range and time in range before the doctor answers.
clinician_context.planall three outcomeslower_bound_ng_per_ml, upper_bound_ng_per_ml, band_citation: the target band as her clinician wrote it.
clinician_context.own_troughs, own_curve_samples, own_dosesall three outcomesHer measured troughs, any post-dose samples, and her dose log, for the charts and "3 of 4 below range".
clinician_context.population_referenceall three outcomesClearance for patients like her, from the same prior the fit used: typical, lower and upper enclosing the central 90%, with genotype_known, source and population_limit (a de novo cohort; show it in Sources). When genotype_known is false the range is built around a mixed-genotype prior and is approximate: label it "approximate".

Settled design details

  • Variability mark, 30%. From the backend constant HIGH_IPV_THRESHOLD_PERCENT (Gavcovich et al., Front Transplant 2025, a convention across many studies). Draw the mark at 30%, and flag the value only when ipv_is_high is true.
  • Time in range has no mark. No threshold is sourced, so the bar runs 0–100% with no line; the value is bold warm when most of the time was outside her range.
  • "Not now" done line: "Not now · flagged for review", tier 3, with "Open".
  • New routes this build adds (patient check-in log, voice fields, question approval, handoff) are specified in section 5.

Section 4

How the agent runs

The agent is a small LangGraph state machine in agent-pk/src/agent_pk/agent/graph.py. The clinical decisions live in evaluate.py as plain functions; the graph only sequences them and owns the pause. Do not move logic into the graph.

  • The model never decides whether the offer exists. The offer node is reachable only after the gate fired.
  • A resume must be "accepted" or "declined". Anything else raises, because a default would be "declined", which silently drops the escalation.
  • Each run clears the previous run's outcomes and sets run_complete only when the view is built. The patient route projects a booking only from a complete run, so a re-evaluated thread never shows a stale booking.
  • Where a language model belongs: turning her free text or voice into typed fields, and phrasing clinician summaries. Everything numerical is Python.
  • Demo limits: one thread (demo-patient-a), an in-memory checkpointer (a restart loses a pending offer), per-process locking, and no authentication by design.

Section 5

Every action, end to end

What the user does, what the agent calls, what comes back, and what the screen does next.

A · The doctor opens the Clinic Board

Evaluate each patient on the list

POST /api/clinician/evaluate with {"thread_id": "demo-patient-a"}. Branch on status, never on which fields happen to be present.

awaiting_decision → the tier-1 decision card

Render from offer: title "Request extra samples?", the burden (burden.extra_draws), the estimate width (expected_gain), and "Decide by" from next_dose_time_h. The chance and predicted range come from prediction, and the band, troughs and population from clinician_context, all in the same response. This card gets the full gradient frame, and there is at most one per board.

review_required → the review card

"Open [name]'s record" with reason as the focus text and stage in Sources. Soft frame; the full frame if nothing else needs a decision. Never count it as steady.

complete → steady, or a flag

clinician_view.action == "no_action" → the flat Steady row. Any other action → a soft-frame card naming the action in plain words. The software never shows a dose amount.

B · The doctor decides on extra samples

"Request extra samples"

POST /api/clinician/decision with {"thread_id": "demo-patient-a", "decision": "accepted"}. Disable both buttons while the request runs.

200 → complete

clinician_view.action is schedule_additional_pk_sample and proposed_sampling is set. Collapse the card into the quiet done line: "You requested extra samples. She now sees the booking in her app." with the chip "Booked · Sun 11 Oct 09:40". The next item takes the full frame.

"Not now"

Same route with "decision": "declined". Completes with action: flag_for_review and no appointment. The card collapses to the tier-3 done line "Not now · flagged for review" with "Open".

409 or 422

409: the thread is not waiting on a decision, so re-run evaluate and redraw; never retry the answer. 422: invalid answer or malformed case; show the detail in the review style. 500: the run finished with no result; show "Could not be evaluated", never steady.

C · Elena opens the patient app

Load her view

GET /api/patient/view?thread_id=demo-patient-a. No agent mount.

Map message to widgets

sample_scheduled → the "Booked by your care team" row, and the evening before, the big timeline widget. contact_your_team → the care team widget becomes the big widget, showing body verbatim. nothing_to_do → no booking widget. Show body only where the message needs it, and never write new software prose around it.

Build the booking widget from next_sample

offsets_post_dose_h [0, 1, 3, 6] → "Before dose · 1 h · 3 h · 6 h". fasted_required: true → "Fasting." Dates come from start_time_h plus reference_instant_utc, rendered in her local time. next_sample stays null until a clinician accepts, and null means no booking widget.

Do not show own_results

The route carries her returned lab values, but the patient app design shows no levels. Don't add them.

D · Elena answers the morning check-in New

Tap one of four equal answers

"Took it" · "Took it late" · "Missed it" · "Not sure". Proposed route: POST /api/patient/log with {thread_id, answer: "taken" | "late" | "missed" | "not_sure", dose_taken_at?}.

The same Thanks for every answer

The answer shrinks to a done row ("Morning dose · Logged · late"), the Thanks widget shows "+1 check-in", the level ring advances, and the next item moves up. Identical for all four answers.

Counts drive levels and badges

Every answer counts. A level every 25 check-ins; badges at 1, 7, 30, 100 and 365 (section 10). No streaks.

E · Elena holds to talk New

Hold the talk button, then release

Show her words as "You said" with the waveform. Only the transcript is used: analysing the voice itself is out of scope and a regulatory risk.

The language model extracts typed fields only

From PATIENT-REPORTED-DATA.md: dose_taken_at, food_within_window, minutes_dose_to_nearest_meal, meal_size_vs_usual (lighter · usual · heavier · much heavier), typical_day. They are sample-validity notes for the clinician, never model inputs.

"Here's what I noted" → confirm

Rows "Dose", "Food", "Typical day?", each with "Change", a picker of allowed values only. "Looks right" logs it (flow D); "Say it again" restarts.

F · The doctor approves a question New

The agent drafts an information-gathering question

It appears on the Clinic Board as "Needs approval": "Send Elena this question?" with the draft as focus text. It never drafts instructions.

Send, or Edit then send

Proposed: POST /api/clinician/question with {thread_id, text, answers, approved_by_clinician: true}. Unapproved drafts must never render in the patient app.

Elena sees "Your care team asks"

Big widget with the approved text verbatim and its answers ("Yes" · "No" · "Not sure"). Answering follows flow D's Thanks.

G · Elena asks a health question New

"Can I take ibuprofen for my back?"

Any health or medicine question becomes the handoff widget: "That's one for your care team. I've sent your question to them and they'll reply here." plus "Call your care team". It is never answered by the app.

Section 9

Clinic Board · cutting through the noise

The board sorts before the doctor reads. Brightness is the attention scale: the one action to take now gets the full gradient frame, what can wait until later today gets a soft frame, and steady patients fade back. Inside a frame, the words to act on are bold with a gradient underline. Web, 1440 wide. Reference: clinic-board-final.html.

Card anatomy

  1. Chip and deadline row. "Decide by Sun 09:40" in bold rose red #C81E54 with a clock icon.
  2. Action title: the action in bold, with thin 300-weight context beside it. For example "Request 3 extra samples? so this estimate can be checked", or "Review: her troughs are running low why she is on your list".
  3. Focus sentence: the exact problem or action in bold with the gradient underline (violet only in tier 2).
  4. Deciding data: the big number, pairs, number lines.
  5. Buttons: primary "Request extra samples", ghost "Not now".
  6. Context under the buttons (13px, hidden by "Supporting detail"): sampling times, "If not now: the estimate still rests on 4 troughs, and nothing can check it until post-dose samples exist.", and "Nothing reaches Elena unless you accept. The software never suggests a dose."
  7. "Sources" disclosure: prediction type, trough dates, clearance source with its de novo population limit, and her own words for a late dose.

Section 14

Accessibility

  • Colour is never the only signal. Every state has a word, and tiers have dot shapes. Out-of-range values have bold type, an arrow and the word.
  • Contrast, computed: body text pairs are at least 4.5:1 in both patient themes. The deadline red is 5.57:1 on white, out-of-range magenta 6.32:1, and badge numbers at least 3:1 on the disc.
  • No text on the gradient.
  • Touch targets: 48px minimum; the talk button 66px.
  • Text scales to 200% without clipping.
  • Charts carry an accessible label with every value, and each dot has a tooltip with its date and whether it was measured or predicted.
  • The patient theme follows the device, with a manual switch in the menu.

Section 15

Tests to write in the frontend

The backend already has these assertions for its routes; the frontend owes the equivalents.

  1. The patient app bundle and network log contain no clinician field. Search responses recursively for prediction, parameters, attributions, probability_below. A top-level check misses nested leaks.
  2. No software-written patient string contains a digit. Exempt only plan text, her own doses and times, booked times and phone numbers.
  3. The four check-in answers produce identical Thanks and an identical +1.
  4. next_sample: null never renders a booking widget, including after "Not now".
  5. review_required always renders a card and never increments the steady count.
  6. A 409 from the decision route re-runs evaluate instead of retrying the answer.
  7. No path joins measured troughs on any chart.
  8. An unapproved question never renders in the patient app.
  9. Reduce-motion and the Motion Off switch leave no running animation.
